# Frontier Hunts — workstream brief (read fully before starting)

Target: Minecraft 1.21.1, NeoForge 21.1.248, Java 21, Mojang mappings at runtime (no refmap needed for mixins).
Players run Sodium + Iris with arbitrary shader packs (Photon etc.) on AMD and Nvidia; everything must work with
shaders off AND on, in singleplayer AND on a dedicated server with several clients.

The user (Austin) wants these features to be the "wait, this is Minecraft?" moment of the mod: cinematic, realistic,
polished, never toy-like or placeholder. Quality bar: /mnt/user-data/uploads/Minecraft-Mod-Builder/HIGH_FIDELITY_RULES.md
(read sections 2-5). Build it to be FINISHED, not a prototype. Keep it performant (100+ FPS is a goal of the mod).
Scope = exactly the feature list in your task. Do not add unrelated features.

- Client classes must never be loaded on a dedicated server (keep them in client packages, referenced only from Dist.CLIENT code).
- Network payload handlers on the server must validate everything (reach, permissions, clamps, rate limits).

## Git workflow (the main repo is /home/claude/fh, branch master)
1. `git clone -q /home/claude/fh /home/claude/work/<ws>` and work ONLY in that clone. Commit to branch `<ws>` there
   (`git checkout -b <ws>`). The coordinator merges your branch; other workstreams run in parallel in their own clones.
2. Compile: `/home/claude/fh/tools/compile.sh /home/claude/work/<ws> /tmp/claude-0/cc-<ws>` (must print exit=0).
   Full jar build (optional, slower): `python3 /home/claude/fh/tools/build.py <ws>-test /home/claude/work/<ws>` -> .build/*.jar
3. Shared files will be merged by git, so keep edits to shared files (hunting/Whitetail.java, HuntConfig.java,
   WildlifeMob.java, client/FrontierSettingsScreen etc.) SMALL, LOCAL and clearly commented (`// [<ws>] ...`). Put your logic
   in NEW classes in a package you own and call them from a few hook lines.
4. JSON resources that other workstreams also touch (lang en_us.json, sounds.json, tags, mixin json lists) must NOT be edited
   directly. Instead write a fragment file that the build deep-merges:
   `patch/_merge/assets/frontierhunts/lang/en_us.json/<ws>.json` (a JSON object with only your new keys),
   `patch/_merge/assets/frontierhunts/sounds.json/<ws>.json`, `patch/_merge/data/.../tags/.../x.json/<ws>.json`,
   `patch/_merge/frontierhunts.client.mixins.json/<ws>.json` (e.g. {"client":["MyMixin"]} — lists are unioned).
   New standalone files (textures, models, blockstates, sounds .ogg) go directly under patch/ mirroring jar paths.
5. Art (textures, models, sounds) must be ORIGINAL and generated by you (Python/PIL/numpy procedural art, Blockbench-style JSON
   models, synthesized audio with numpy -> .ogg via ffmpeg/oggenc if available). High quality, matching the mod's existing
   look (inspect existing textures in merged62g8.jar). Render previews of new art to PNG and look at them before committing.
6. You cannot launch Minecraft (the coordinator does in-game testing on the user's PC). So: compile, write offline unit/harness
   checks for pure logic where practical, reason carefully about runtime behaviour, and review your own code for
   crashes (NPEs on client/server split, missing registrations, missing lang keys, missing textures).
7. When done, write `docs/ws/<ws>.md` in your clone: what you built, files changed (esp. shared files + exact hook lines), config
   options, commands, and an exact numbered IN-GAME TEST SCRIPT the coordinator can run (commands to spawn/force states,
   what to look for). Commit everything, then report back a concise summary (< 600 words) including the branch name and
   anything the coordinator must do (e.g. settings-screen entries you could not add).
